# Лабораторная 5 — Создание и завершение процесса

**Курс:** Операционные системы, 01.09.2025–31.12.2025

## Задание

### 1. Жизненный цикл процесса

Программа, которая создаёт и инициализирует переменные (локальную и глобальную),
выводит их адреса и содержимое, выводит pid, порождает процесс через `fork(2)`;
в дочернем выводит pid и parent pid, адреса и содержимое переменных, изменяет их
и выводит снова; в родительском выводит содержимое переменных и делает `sleep(30)`;
дочерний завершается с кодом 5 через `exit(2)`, родительский дожидается его,
вычитывает код завершения, выводит причину и код. **В каком случае кода завершения
не будет?** Понаблюдать за адресными пространствами в procfs и за состояниями
процесса через `ps`.

### 2. Процесс в состоянии зомби

Модифицировать программу так, чтобы дочерний процесс становился зомби. Объяснить,
какую проблему решает это состояние. Может ли родительский процесс оказаться
зомби, и что тогда произойдёт с дочерним — смоделировать.

### 3. Создание процесса через clone(2)

Создать процесс через `clone(2)`, память под стек выделить `mmap(2)` так, чтобы
регион был связан с файлом и синхронизировался при записи. Написать две функции:
точку входа нового процесса и функцию, выделяющую на стеке массив со строкой
«hello world» и рекурсивно вызывающую себя с глубиной 10. Исследовать полученный
файл: найти строки «hello world» и объяснить их количество, найти счётчик
рекурсии и адреса возврата.

## Сборка и запуск

```bash
gcc main1.c -o main1 && ./main1

# зомби — смотреть во втором терминале, состояние Z
gcc main2.c -o main2 && ./main2 &
ps -o pid,ppid,state,comm

# сирота — PPID дочернего меняется на 1
gcc main3.c -o main3 && ./main3
```

## Что показывает работа

После `fork` адреса переменных в родителе и потомке совпадают, а значения
изменяются независимо — это copy-on-write: виртуальные адреса те же, физические
страницы расходятся при первой записи.

`main2.c` показывает зомби: дочерний завершился, но родитель не вызвал `wait`,
поэтому запись в таблице процессов остаётся — ядро держит код завершения до тех
пор, пока родитель его не заберёт. Это и есть смысл состояния: без него код
завершения потерялся бы между `exit` потомка и `wait` родителя.

`main3.c` показывает обратный случай: родитель завершается первым, и осиротевший
процесс усыновляется init/systemd — его PPID становится 1, и уже init вызывает
`wait`, поэтому зомби не накапливаются.

Ответ на вопрос из задания: кода завершения не будет, если процесс завершился не
сам, а по сигналу — тогда `WIFEXITED` даёт ложь, и смотреть нужно `WIFSIGNALED`
и `WTERMSIG`.
